# RK3288 双机推流实测与开发反馈

## 范围与证据

本轮延续[局域网验证计划](../plans/2026-10-17-rtmp-lan-validation.md)，两台依次运行；接收仅限本机局域网，视频解码到空输出，不录像。应用画面由临时控制器遮黑，像素检查仅在设备内存进行。每段结束或失败退出主应用、返回桌面、卸载控制器并移除本段精确防火墙规则。

固定主APK的SHA256为 `e6577d21e789e6d06409077e0f76b2c26fba7282e8ef26ef9d38cc2e3301a9db`，真实OpenCV+ncnn双ABI构建；本轮不修改生产代码或APK。最新版控制器SHA256为 `0aedc1cd977b20209b3b8d0af9fd592d9f632cb84496715f6194af9221837e3d`。编译启用ncnn不等于本轮已验证某个实际模型的推理精度或有效后端。

本地聚合证据位于 `cache/rtmp-lan-2026-10-17/`，不包含截图、录像或原始敏感日志；该目录被忽略，不能称为已入库备份。原始失败结果保留，不以复验通过覆盖。

## 实测结果

| 项目 | 机A | 机B |
|---|---|---|
| FFmpeg n6.0实际加载、合成文件转推30秒 | 通过，454帧 | 通过，454帧 |
| 相机稳定段 | 本轮304.9秒、3921帧、12.86fps；首轮305.3秒、3804帧、12.46fps亦保留 | 304.9秒、3991帧、13.09fps |
| 正常停止/重启 | 首次125→0帧失败；后续127→186帧复验通过，首次原因未定 | 133→196帧，通过 |
| 受控断流后显式重试 | 104→316帧，通过 | 118→327帧，通过 |

机B稳定段接收端exit0、解码错误行数0；正常重启两段均exit0。断流用例第一接收进程被主动终止，exit1符合注入预期，最后接收进程仍须exit0且实际收到帧。上述重试是控制器调用现有停止/启动入口，不是自动重连能力。

请求配置来自 `MainActivity.startRtmpPush()` 与 `FfmpegRtmpPusher.startInternal()`：640×480、15fps、RGBA输入、libx264、ultrafast、zerolatency、YUV420P输出，无音频。表内fps为总解码帧数除以推流请求至结果事件的主机墙钟时间，包含启动/停止开销；不是相机独立帧率或人脸识别帧率。

## 资源采样

机B稳定段PSS共10个有效样本：87,946–89,851KiB，中位89,286KiB（约87.2MiB）。独立RSS采样中途开始，有效46个样本：212,664–216,740KiB；RSS与PSS定义不同，不混用为内存增长证据。

机B末段补采CPU共9个有效区间：单核口径152.38%–159.65%，中位155.05%；四核设备上的该口径允许超过100%。Android没有 `getconf`，从同一内核32位工具进程辅助向量的AT_CLKTCK实际读取100，再按目标进程utime+stime增量计算，未猜测时钟频率。早期CPU空值保留为空，不补造数据。

机B有效RSS窗口线程数59–60；CPU频率节点观测1,008,000–1,608,000kHz。`soc-thermal`的温度节点原始整数观测56,972–65,831；本轮未核实板级换算和阈值，不仅凭该数值或频率变化断言热降频。

机A本轮300秒段有53个有效RSS样本：192,424–217,572KiB，中位206,372KiB；CPU有52个有效区间：单核口径157.45%–166.48%，中位162.165%。线程数39–59（包含启动/退出阶段）；CPU频率节点观测1,416,000–1,608,000kHz，温度节点原始整数56,034–67,982。

机A的300秒段仍未取得有效dumpsys PSS。追加独立60秒相机段 `memorycheck1`（实际61.2秒、780帧、全部守卫与清理通过），8次查询确认dumpsys TOTAL的PSS列均为0，而同一进程smaps的Pss字段可读。将各映射Pss求和得到45,356–99,322KiB，中位91,638KiB；首个样本包含应用启动，整组不冒充稳态或300秒窗口的PSS峰值。仅保存数值和映射数量，没有保存映射地址、路径或原始输出；未root或修改系统。dumpsys为何在该设备返回0仍未定位到系统内部根因。

两台采样窗口、热状态和辅助采集开销不同，不能据此作受控A/B性能比较。独立采样器通过ADB只读取白名单系统数值，原始命令输出在内存解析后丢弃。汇总的 `complete_two_device_metrics` 保持false，含义是两台300秒窗口的PSS没有全部覆盖；机A独立补采按 `supplementary_pss` 另列，不改写旧缺测。

完整数值与文件摘要见本地 `runtime-metrics-summary.json`；采集脚本为 `collect-runtime-metrics.py`，汇总脚本为 `summarize-runtime-metrics.py`。均为本次临时工具，不自动运行、不接入生产。

最终工具白名单源码（含旧标签取消标记）已打包为本地 `runtime-validation-tools-b3f1afa502e2.zip`，22项文件摘要见 `runtime-tools-source-binding.json`。该包是最终工具版本快照；机B第一RSS窗口使用尚无auxv回退的初版采集器，不声称所有历史数据都由最终版本逐次生成。原控制器源码与APK绑定继续保留，不覆盖旧快照。

## 问题定位与最短后续路径

1. **机B遮挡失败的定位**：此前366个非黑采样属于本应用Toast，处理Toast后仍有4点，独立应用黑窗未解决。源码与运行时又发现StatusService的独立状态悬浮窗；最新版控制器仅透明处理本进程已知状态窗，严格守卫未放宽。本轮300秒真实相机、重启、重试均通过，支持状态窗干扰这一解释；未做单独开关状态窗的相机A/B实验，不宣称已证明唯一根因。正式隐藏预览须覆盖独立窗口和首帧，仍属后续功能。
2. **15fps请求值未达**：两台当前接收吞吐低于15fps。最短下一步是在帧获取、RGBA拷贝、回环写入和编码四段增加匿名耗时计数，再决定是否优化。`RtmpCameraInput.pump()` 在读帧/写帧后额外sleep固定间隔，处理耗时会叠加在间隔上，这是待测候选，不据当前数据直接改节奏或归因为编码瓶颈。
3. **首次重启异常尚未闭环**：机A旧首轮重启0帧仍保留，后续通过只证明可复现成功路径。下一步固定同一包和接收器，记录有限状态事件、首个解码进度和接收端退出码，复现失败后再修复；不得用自动重试掩盖首次失败。
4. **内存与CPU仅为阶段数据**：PSS、RSS、CPU和频率共同记录，不能以短段稳定宣称无泄漏或通过满档内存预算。机A的dumpsys零值须继续显式判无效；授权且可读的smaps可作为标明来源的补充，不能把零值当低内存通过。后续应固定模型profile、节流模式和场景，再做长时间采样；不采身份、特征向量或画面。
