# 桌面助手终端 —— 产品愿景与关键设计决策

本文是**愿景与关键决策**文档，**不是实现记录**。除明确标注"已存在"的既存组件外，文中所述功能**全部未实现**。不得据此宣称任何能力"已落地""已实现""已验证"。

**本文的职责边界**（遵循 `docs/DOC_STANDARD.md` §3 单一事实源）：设备能力事实引用 `docs/RK3288_CONSTRAINTS.md`、`docs/capability-matrix.md`、`docs/research/rk3288-device-capability-survey-2026-09-17.md`；指纹与读卡外设的接入设计引用 `docs/designs/rk3288-fingerprint-integration-design.md`。本文只写"这套东西是什么、为什么这样设计、哪些还没定"，不重述上述文档的结论。

## 1. 定位扩张声明

本项目现自称"多模态人脸识别系统"。本文提出的方向把它扩张为：

> **个人桌面助手终端** —— 由一台笔记本电脑（主控与主存储）与两台 RK3288 设备（展示与交互）组成的三节点系统。人脸 / 指纹 / 刷卡从"产品本体"变为这套系统的**身份与授权层**。

这是一处**范围决定**，已由用户于 2026-09-22 确认。它意味着 `README.md` 与 `CLAUDE.md` 的项目简介在功能落地后需要同步改写——**本文不代改**，由后续任务承接。

## 2. 系统拓扑与设备形态

三节点：笔记本 + 机 A（`192.168.5.2`）+ 机 B（`192.168.5.3`），经交换机组成局域网。另挂一台打印机，非本系统节点。

| 节点 | 职责 |
|---|---|
| 笔记本 | 主存储、主控、联网抓取、信息整理、**唯一事实源** |
| 机 A / 机 B | 展示、交互、本地身份认证、离线缓存 |

### 2.1 两种设备形态

| 形态 | 内容 | 说明 |
|---|---|---|
| **投屏态** | 把笔记本桌面延伸到设备，**含触控** | 由用户手动开启（沿用现有 spacedesk 路径）。成本已知：实测该路径占 **51–55% 单核、整机 Idle 仅剩 13%**，且**完全不使用 VPU**（`docs/RK3288_OPTIMIZATION.md`） |
| **信息流态** | 设备**自己渲染**信息流卡片 | 不依赖投屏，资源开销可忽略；支持简单交互 |

物理实况：笔记本支架会挡住其中一台设备。因此常态是"一台投屏态兼额外操控 + 一台信息流态"。

### 2.2 性能指标的归属

**各设备展示自己的性能数据，设备之间不同步。** 投屏态才看笔记本数据，且由用户手动开任务管理器拖过去——**不在本系统范围内**。

## 3. 通信与离线拓扑

需求（用户 2026-09-22）：有笔记本时由笔记本作唯一事实源、实时同步与控制；**笔记本离线时 `.2` 与 `.3` 之间互通同步**；重连后双向同步。

> ⚠️ **"离线双机互通"这一条决定了整个安全模型。** 它要求两台设备**也必须是服务端**，因此拓扑不是"1 个服务器 + 2 个客户端 + 1 个令牌"，而是 **3 个节点两两互相认证**。这一条改变的是认证的**方向性**（必须双向），不只是数量。

建议方案（**待确认**）：

| 维度 | 建议 | 理由 |
|---|---|---|
| 传输 | 内网 HTTP + Bearer token 起步 | 门禁不做（§10），故不预留公网级加密余量；若将来接入更高价值场景须重新评估 |
| 认证 | **双向**，每对节点一个预共享凭据（共 3 对） | 离线双机互通迫使设备也是服务端 |
| 推送 | **WebSocket** | 设备重连要拉增量、笔记本要实时推，**两个方向都需要**；SSE 单向不够 |
| 发现 | **写死 IP** | 固定 3 节点，引入发现机制只增加故障面 |

## 4. 时间与顺序（本设计最硬的一条约束）

### 4.1 已实测事实

两台设备**系统时钟未校准，且彼此相差约 13 天**——分别停在 `2017-01-15 22:40:48 CST` 与 `2017-01-02 00:23:47 CST`（出处：`docs/RK3288_OPTIMIZATION.md` §2.4）。

> **后果：任何"按时间戳判胜负"的合并策略在这套设备上是错的。** 两台离线各改同一条待办，时钟落后 13 天的那台**永远输**——表现为"我明明在这台上改了，一联网就被回滚"。这是一个从表面看毫无线索、只能靠实测数据推出的失效模式。

### 4.2 两条必须分离的机制

| 目的 | 机制 | 为什么不混用 |
|---|---|---|
| **冲突排序** | **逻辑版本号**（每次改动递增） | **完全不依赖墙钟**，从根上避开 13 天偏差 |
| **时间显示与提醒触达** | **由笔记本经 adb（root）下发校正设备时钟** | 见 §4.3 |

### 4.3 时钟同步：由笔记本经 adb 下发

用户 2026-09-22 指定实现方式：**由笔记本负责**，沿用其既有脚本——**经 `adb shell`（root）下发时间**。该路径成立的前提已具备：`adb shell` 在本设备上默认即 `uid=0(root)`；两条 TCP adb 目标（`192.168.5.2:5555` / `192.168.5.3:5555`）已在使用。

> **为什么应用层做不到、而这条路径可以**：`SET_TIME` 是系统级权限，普通 Android 应用不可获得；而 `adb shell` 在本机以 root 运行，故可设置。
>
> ⚠️ **设置系统时钟是设备状态写入**，属受控操作。本文只记录该机制**由用户指定**，不代表它已被纳入自动编排、也不代表可以被自动执行。

**同步时机与残留问题**（设计必须覆盖）：

| 场景 | 行为 |
|---|---|
| 笔记本服务启动 | 立即向两台设备下发（用户要求"第一件事"） |
| **设备重启后** | **时钟退回未校准状态**（本机无网络授时）→ 需在**设备重连时重新下发**，不能只做一次启动同步 |
| **两台离线互同步期间** | 无校时来源 → 估时精度下降，**界面须显式标注为估算** |

> ⚠️ **校时不能取代逻辑版本号。** 即使时钟被校正，下列情形仍会产生不可靠比较：设备离线期间无校时来源、设备重启导致时钟回退、两台在同一秒内各改同一条待办产生并列。
>
> **因此 §4.2 的分工不变：时间戳只用于"显示"，冲突排序一律走逻辑版本号。** 校时解决的是"**显示对不对**"，不是"**谁先谁后**"。把这两件事混为一谈，就会写出"时钟校正后就不需要版本号了"这类错误结论。

## 5. 设备锁与隐私

### 5.1 要保护什么

防止未经授权的人员**阅读**设备内容，或**操作**设备导致数据被改乱。

### 5.2 可用的认证手段：现状与"利用现有功能"的落差

用户要求"利用好现有设备功能"认证。**但按仓库已实测的事实，今天真正可用的只有人脸一项**：

| 手段 | 现状 | 出处 |
|---|---|---|
| **人脸识别** | ✅ **已实现**，本项目核心能力 | `docs/capability-matrix.md` §2.1 |
| 指纹 | ❌ **零行实现**（仅有设计稿，无 helper、无 `SG_IO` 客户端） | `docs/designs/rk3288-fingerprint-integration-design.md` |
| 刷卡 | ❌ 对主机**零流量**，**当前不可用** | `docs/capability-matrix.md` §2.5 |
| NFC | ❌ **无 Android NFC 协议栈**，`NfcAdapter` 不可用 | `docs/capability-matrix.md` §2.5 |
| 声纹 | ❌ 未实现（麦克风硬件存在） | — |
| 蓝牙 | 硬件与协议栈存在、**当前未启用** | `docs/RK3288_CONSTRAINTS.md` §0.4 |

> **结论：设备锁的第一版只能建立在人脸之上。** 指纹与刷卡要等各自接入完成后才能作为认证手段并入。这是需求描述与设备实测之间的**真实落差**，必须先讲明再设计。

### 5.3 锁屏是"对外可见投影层"

设备锁与信息流态**存在目的冲突**：自动锁定会停止展示信息流。因此设计必须区分两种可见性：

| 态 | 显示内容 | 可见性假定 |
|---|---|---|
| **锁定态** | 仅为**用户自定义的锁屏内容** | 假定"旁人可见" |
| **解锁态** | 完整信息流（待办、消息、总结）+ 交互 | 仅本人 |

> **由此反推出一个必然设计：信息流条目必须携带"可见性分级"**——哪些允许在锁定态展示（如节假日倒计时、今日天气），哪些必须解锁后才能看（如待办、微信消息、B站总结）。这不是额外需求，而是"锁屏内容可自定义"+"自动锁定"两条需求同时成立时的**逻辑后果**。

### 5.4 备用解锁：PIN 由笔记本统一下发

用户 2026-09-22 决定：**PIN 由笔记本统一下发与控制**；并明确"**本身质量功能必须合格**"。该机制必须同时满足三条约束——**缺任何一条都会退回致命失效模式**：

| 约束 | 要求 | 不满足的后果 |
|---|---|---|
| **离线可用** | 设备**本地缓存** PIN 的校验值，离线时**本地**校验 | 若每次解锁都要问笔记本，则"笔记本离线 + 人脸失效"→ **设备锁死**，正是要避免的那个失效模式 |
| **明文不出笔记本** | **由笔记本侧完成 KDF，下发给设备的只是派生值**；明文 PIN 永不落设备、不过网络 | §3 传输是内网 HTTP，无加密余量；明文 PIN 过网即被内网嗅探获得 |
| **可轮换 / 吊销** | 笔记本可随时下发新值并使旧值失效 | 这是"统一控制"的实际内容；做不到就只是"一次性设置" |

> **KDF 必须用慢哈希。** PIN 熵极低——4 位数字仅 10⁴、6 位仅 10⁶ 种可能。快哈希在校验值泄漏后可被瞬间穷举，慢哈希是唯一实际屏障。

### 5.5 其余失败回退与质量要求

1. **必须有非人脸的备用解锁**（即 §5.4 的 PIN）。**否则摄像头一旦故障或被遮挡，设备即永久锁死**——单一人脸认证的致命失效模式。
2. **误接受率是安全参数**，须显式设定目标值。**不得沿用识别场景的宽松阈值**——识别场景的代价是"认错人"，锁场景的代价是"放错人进门"。
3. **尝试次数限制与退避**，**人脸与 PIN 两侧都要有**（慢哈希只防"拖库后离线穷举"，防不住"对着设备一直试"）。
4. 人脸模板沿既有加密存储（`FeatureTemplateEncryptedStore`），**不新增任何明文落盘**。

### 5.6 边界：设备锁保护不了投屏内容

投屏态下内容源在笔记本，锁住设备屏幕**并不能保护**镜像过来的数据。设备锁的有效范围是**设备自身拥有的数据**。

## 6. 信息源与离线分级

| 信息源 | 来源 | 笔记本离线后 |
|---|---|---|
| **B站动态与总结** | 笔记本抓取 + Claude 整理 | ❌ **不可能离线**（需联网） |
| **天气** | 外部 | ⚠️ 缓存，**必须标注数据时间**，不得伪装为实时 |
| **待办** | 用户经 Claude 对话、或经微信 bot 输入 | ⚠️ 缓存 + 本地可改（改动走逻辑版本号合并，§4.2） |
| **节假日与调休** | 年度静态表 | ✅ 完全可离线。⚠️ **农历与调休表须每年更新**，属长期维护项 |
| **游戏日活 / 周常** | **本地周期推算** | ✅ 完全可离线 |
| **游戏活动** | **用户手动输入**（Claude 对话 / 微信 bot） | ❌ 需用户输入 |

> **"离线可用"必须按此表分级承诺**，不得笼统宣称"离线可用"。前两类中真正无条件的只有节假日与游戏周期两类。

## 7. B站自动化

### 7.1 范围（用户 2026-09-22 修订）

1. 读出账号所关注 UP 主的**全部动态更新**；
2. 逐个检查，**把含抽奖的挑出来告知用户**；
3. **用户自己转发**（系统不代转）；
4. 按用户偏好，把动态中的投稿**自动加入"稍后再看"**；
5. 对内容**生成总结**。

用户明确要求：**必须检查登录态，未登录则直接停止**，不得继续；若无公开接口，**在网页内调试以定位接口**（个人自用，无其他顾虑）。

**风险分级**：本方案只含"**读 + 一个低危写**（加稍后再看）"。**不自动点赞、不自动转发抽奖**——原需求中的这两项因属账号风控打击行为，经讨论已**移出自动范围**。这是本轮对用户原始需求的一处**主动收窄**，记录在此以免日后被误当作遗漏。

### 7.2 实现载体的两段式划分

| 阶段 | 工具 | 理由 |
|---|---|---|
| **侦察**（定位接口） | **Chrome DevTools MCP**（Chrome 官方） | 它本就是给编码 agent 调试网页用的，正是"在网页里调试找接口"的拿手活 |
| **生产**（每日无人值守） | **Chrome 扩展** | 见下 |

> ⚠️ **"用现有 Chrome 的登录态"有一处硬限制，必须写在这里**：Chrome 自 **136 版**起，`--remote-debugging-port` 对**默认 profile 直接失效**，必须额外指定非默认的 `--user-data-dir` 才生效。官方理由是防止攻击者挂到真实 profile 上窃取状态——即"**驱动你正在用的那个 Chrome**"正是它**专门要阻止的行为**。且调试端口**没有任何认证**，谁能连上谁就获得全权控制。

**因此生产形态选扩展**：扩展在真实 profile **内部**运行，不需要调试端口、不需要 profile 锁、不需要重新登录——恰好实现"用我现有的登录态"，且暴露面小得多。

## 8. 微信桥

**已核实为官方渠道**（**不是**注入式外挂）：腾讯已开放个人 Bot API（iLink / ClawBot），并发布了官方使用条款。已有 MCP server 给出 Claude Desktop 的接入配置。

用途（用户 2026-09-22）：**双向**。用户发消息给 bot 以录入待办与游戏活动；系统也可**主动发消息**给用户。

**边界与未核实项**：

1. **未读官方《ClawBot 功能使用条款》**——落地前必须读。本文**不代为断言其无限制**。
2. **主动推送的实际行为未独立验证**：用户陈述为双向，本文**采信但标注为未独立复核**。这是"提醒"类功能的命门，建议实现前先做最小验证。
3. 已知边界（来自 Hermes 官方文档）：扫码连接的是一个 **bot 身份**（形如 `<id>@im.bot`）而**非个人微信号**；该身份**通常收不到普通微信群消息**。私聊不受此限。

## 9. 与现有项目的关系

用户 2026-09-22 决定：**不新建仓库、不建复杂中枢**——"就是写几个脚本，推送信息的事"。

因此数据流复用一个已存在的通道：

```text
Claude Desktop（笔记本）
  ├─ 脚本：B站抓取与总结、天气、节假日
  ├─ 微信 MCP：收你的消息 / 给你发消息
  └─ 待办：你在对话中直接输入
         ↓ 整理为信息流条目
  现有 Windows 本地服务（HttpFacesServer）
         ↓ 新增端点，推送给设备
  设备端 App（.2 / .3）
         ├─ 信息流面板
         ├─ 设备锁
         └─ 转发给插件 / 独立软件
```

> ⚠️ **通道复用前必须先改一处**：该 Windows 服务**当前仅监听 `127.0.0.1`**（`docs/capability-matrix.md` §2.2 将其列为"限制"项，属**有意设计**）。要让它对设备可见，**必须改变监听范围**——这是一次**安全边界的调整**，须单独确认后再动。

### 9.1 认证能力应沿用既有"加速契约"范式

设备侧认证能力（人脸 / 指纹 / 刷卡 / 麦克风）应作为**正式内容，不做插件**——认证路径上做动态加载等于给安全关键代码开后门。

但应**复用本仓库已有的能力声明范式**：加速契约的 `requested` / `effective` / `evidence` / `reason` 四元组，固定原因码含 `missing_dependency`、`unsupported_platform`。即"这台没有指纹"应**显式报 `missing_dependency`**，而非静默降级。该范式在本仓库已有 CI 行为测试（见 `CLAUDE.md` 加速契约一节），**不必新发明**。

### 9.2 "自动"的触发器：机制已存在，需选定一个

> **一处更正**：本文初稿把"自动发布缺触发器"写成**真实缺口**，这是判断过头了。核实结果：**触发机制已存在**——本仓库已在用时间驱动的 loop（`LOOP.md`：`/loop 1d Run $loop-triage`），且本会话可用的 **scheduled-tasks 调度服务**存在并响应正常（当前**零任务配置**）。**因此缺的不是机制，而是"选哪一个 + 任务内容是什么"。**

需要区分两类机制——**这一点极易混淆**：

| 机制 | 性质 | 能否当"每天的钟" |
|---|---|---|
| **Claude Code hooks** | **会话内的事件驱动**（`PreToolUse` / `PostToolUse` / `SessionStart` 等） | ❌ **不是时钟**。有事件才触发，没事件不触发 |
| **`/loop` · scheduled tasks** | **时间驱动** | ✅ 这才是"每天跑一次"的载体 |

因此"每日抓取 B站并发布"应由**时间驱动**的那一类承载；**hooks 适合承载"某个动作发生时顺带做点什么"，不适合承载"到点自动跑"**。二者常被混为一谈，是因为名字听起来都像"自动化"。

## 10. 不做什么

- **不做门禁**（用户 2026-09-22 决定）。但**设备锁本身的质量必须合格**（§5.4、§5.5）——不做门禁不等于可以放低锁的标准。
- **不自动点赞、不自动转发抽奖**（§7.1）。
